## Distinguishing expected conflicts from genuine failures

Every non-2xx response this test provokes is expected to be a transient race, not a bug: the idempotency-key race (two requests, same key, landing inside each other's transaction) surfaces today as an unmapped `DataIntegrityViolationException` -> HTTP 500 (there's no dedicated 409 for this specific race, only for a reused key with a *different* body -- a rough edge worth knowing about, not fixed here since it's a production-code change outside this audit's scope). The harness treats any HTTP 500 as retryable with the SAME Idempotency-Key and keeps retrying (up to 50 attempts) until it sees a 2xx. Any other status (400/403/404/409/422), or exhausting the retry budget, is counted as a genuine failure -- the table above reports whether any occurred.

## Limits of this result

This is a reproducible correctness/stress test run against a single local machine and a single-node dev Postgres. It proves the double-entry and idempotency invariants hold under real concurrent load at this scale and on this hardware -- it is **not** a production capacity/scalability benchmark (no network latency, no managed-DB connection limits, no multi-instance contention as in the k3s deployment), and it is **not** a formal proof (no model checking, no exhaustive interleaving search) -- it's evidence from one, repeatable, adversarial run.
